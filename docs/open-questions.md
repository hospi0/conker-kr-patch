## 1b. ~~`0xBD` 로 이어진 대사의 폭~~ → **해결 (실기 확인)**

`0xBD` 도 자막 분리자다. 추출 함수는 `0x00` 만 보지만, 메시지 활성화 시 게임이 버퍼의
`0xBD` 를 제자리에서 `0x00` 으로 치환한다. 페이지별로 측정되며 말풍선은 그 최대폭으로
한 번 정해진다 — `docs/bubble-width.md` §3.

## 2. 자모 자형 설계

11×12 안팎, 4비트 안티에일리어싱. 초성 2벌 + 중성 1벌 + 종성 1벌 = 86자모가
89칸에 들어간다. 겹쳐 그리기 전제이므로 각 자모의 `xoff`/`yoff` 배치 규칙을 먼저 정한다.

## 부록 A — 매핑을 어떻게 찾았나

정적 분석은 **전부 0건**이었다. 다시 시도할 필요 없다.

| 가설 | 검색 범위 | 결과 |
|---|---|---|
| 1바이트 char→glyph 인덱스 테이블 | ROM 64MB + RDRAM 8MB 전수 순열검색 | 0건 |
| BE16 상대 오프셋 테이블 | ROM + RDRAM (고유율 제약 포함) | 0건 |
| BE32 절대 포인터 테이블 | ROM + RDRAM | 0건 |
| `c-'A'` / `c-'a'` 산술 체인 | ROM + RDRAM | 디버그 폰트 외 0건 |
| 체인 워크 `ptr += *(u32*)(ptr+4)` | RDRAM | 0~1건, 그 1건은 힙 정렬 루틴 |
| RDRAM 에 디코드된 글리프 비트맵 | 글리프 5종 × 4포맷 (패딩 포함 재시도) | 0건 |

**왜 0건이었나**: 순열검색은 `table[charcode] = index` 를 가정했는데
실제 테이블은 **반대 방향**(`table[index] = charcode`)이었다.
그리고 글리프는 렌더 시점이 아니라 **부팅 때 한 번만** 읽힌다.

**푼 방법**: `0x802C97F0` read 브레이크포인트.
대사 중엔 안 걸리고 하드리셋 직후에만 걸린다는 사실 자체가
「부팅 전처리」라는 답이었다. 레지스터의 `T5 = 0x80085994` 를 따라가니
글리프 메타 배열이 나왔고, 그 바로 앞에 매핑 테이블이 붙어 있었다.

> **교훈: 테이블 검색이 0건이면 방향(키↔값)이 반대인지 먼저 의심한다.**
> 그리고 「언제 읽히는가」는 「어디에 있는가」만큼 중요한 단서다.

## 부록 B — 폰트를 어떻게 찾았나

폰트 탐색에도 상당한 시간을 태웠다. 실패한 시도:
폭 테이블 스캔 / 글리프 격자 주기성 검출기 / 엔진 데이터·꼬리 애셋 렌더링 /
텍스처 크기 리프 스윕 / `font`·`glyph`·`char` 문자열 grep — **전부 0건**.

이유는 단순하다. **폰트가 rzip 압축 블록 바깥의 비압축 섬에 있었다.**
압축 애셋을 뒤지는 어떤 방법으로도 나올 수 없었다.

결국 **스페인어 패치 xdelta 를 적용해 원본과 바이트 diff** 를 뜨자 한 번에 끝났다.
바뀐 곳이 헤더 CRC 8바이트 + 폰트 2구간 + 대사 구간, 그게 전부였다.

> **교훈: 대상 게임에 이미 다른 언어 팬번역 패치가 있으면, 블라인드 리버싱 전에
> 그 패치부터 diff 한다.**

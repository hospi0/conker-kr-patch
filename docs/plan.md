## 1. 글리프 엔트리 규격 (전부 실기 검증됨)

```
헤더  [w][h][xoff][yoff][BE32 엔트리총크기]      8 바이트
본문  RLE 픽셀,  바이트 = (명암4비트 << 4) | (런길이 - 1),  런길이 1..16
```

### ★RLE 런은 행 경계를 넘으면 안 된다

디코더 열 루프는 `while t1 < w+1` 로 **행 끝에서 그냥 끊고 넘친 픽셀을 버린다.**
다음 행은 **그 다음 RLE 바이트**부터 시작하므로, 행을 넘나드는 런을 쓰면 2행부터 전부 어긋난다.

> 검증: 원본 95글리프를 **행 단위로** 재인코딩하면 바이트까지 100% 일치한다.
> (평면 인코딩은 21/95만 일치. 「평면 재인코딩으로 285B 이득」은 이득이 아니라 깨진 인코딩이었다.)

### 디코더가 만드는 텍스처

```
텍스처 = (w+1) x (h+1),  픽셀버퍼 stride = (w+1+7) & ~7,  글리프당 224 B 슬롯
행 0        : 전부 0 (테두리), RLE 소비 안 함
행 1..h+1   : 열 0 은 0 (RLE 소비 안 함), 이후 RLE 로 w 픽셀
              홀수 행은 바이트 인덱스 ^= 4  (N64 8bpp 스위즐)
              행 끝 남는 열은 0 으로 채움
```

디코더는 **h+1 행**을 소비하므로 마지막 한 행분(w 픽셀)을 다음 엔트리 헤더에서 읽는다.
헤더 첫 바이트가 작은 w/h 라 상위니블 0 → 투명이라 무해하다.

## 2. 렌더러

```
레이아웃 (RDRAM 0x802D0B14~)   pen += (w+1) + xoff - 1   =   pen + w + xoff
                               line_h = max(line_h, yoff + (h+1)),  최소 12
                               줄 폭 = max(줄별 pen)        -> 말풍선 크기의 근거 (확정)
그리기   (RDRAM 0x802D0210~)   draw_x += xoff * scale
공백 0x20                       advance 4  (문자 룩업이 0x60 을 돌려주고 그 분기에서 +4)
줄바꿈 0x0A                     줄 종료
```

`yoff` 는 **양수 = 아래로** (숫자 0, 대문자 1, `-` 4, `.` 6, `,` 7 로 확인). 패치 불필요.

### ★advance 와 그리기 이동이 한 값(xoff)에 묶여 있다

→ 초·중·종성을 한 칸에 겹치려면 **세 조각 모두 `w = 진행폭`** 이어야 한다.

```
셀 12px + 자간 1 = 진행폭 13
초성      : w=12, xoff=+1   -> advance 13,  pen 기준 +1 에 그림
중성/종성 : w=12, xoff=-12  -> advance  0,  같은 자리에 겹침
```

`w=12`(원본 최대 11 초과)도 정상 동작한다.

### 렌더러 패치 — 블록 66 (ROM `0x6BDA2`, 로드베이스 `0x802D0000`) 세 곳

| 오프셋 | 원본 | 패치 | 내용 |
|---|---|---|---|
| `+0x210` | `90990002` | `80990002` | `lbu` → `lb` (그리기 xoff 부호화) |
| `+0x21C` | `07210004` | `10000004` | `bgez $t9,+4` → `b +4` |
| `+0xB2C` | `904D0002` | `804D0002` | `lbu` → `lb` (레이아웃 xoff 부호화) |

⚠️ **`+0x21C` 를 빼면 안 된다.** `lui $at,0x4F80` + `bgez` + `add.s` 는 unsigned→float 변환
관용구다. `lbu` 전제이므로 부호 있는 xoff 에 **2^32 가 더해져** 글리프가 화면 밖으로 날아간다.

압축 해제 27MB 전수 검색으로 각 1곳뿐 확인. 패치 후 재압축 여유 +38 B.

## 3. 문자코드 처리

### 코드 → 글리프 인덱스 룩업 (RDRAM `0x802D0C40`)

```
0x61..0x7A       ->  -0x20  (단일 케이스 접기)
0x20 (공백)      ->  0x60 반환 (공백 센티널)
그 외            ->  charmap 95칸 선형 스캔, 일치하는 슬롯 번호 반환
못 찾으면        ->  ★원래 문자코드를 그대로 반환 (범위 밖 메타를 읽게 된다)
```

### 문자 디스패치 (RDRAM `0x802D09A0`)

```
코드 < 0xA1      ->  정상 글리프 경로
0xA1 ~ 0xA7      ->  건너뜀
0xA8 ~ 0xFF      ->  jal 0x850415e0  (특수 토큰 경로 — 일반 글리프 아님)
```

⚠️ **자모에 0xA1 이상 코드를 쓰면 안 된다.** 원본 charmap 의 악센트 코드 31개가
전부 0xA8 이상이므로 `0x80~0xA0`(비어 있고 안전) 으로 재배정한다.
원래 코드는 영문 텍스트에 안 쓰이므로 미매핑이 되어도 안전하다.

⚠️ **charmap 을 전량 재배정하면 안 된다.** 영문 코드가 미매핑이 되면 렌더러가
없는 글리프의 메타를 읽어 RDP 에 쓰레기 치수를 넘기고 **화면 전체가 깨진다**.
자모는 기존 슬롯의 코드를 물려받되, 0xA1 이상만 옮긴다.

## 4. 부팅 로더

```
서술자   RAM 0x80082F80 + fontid*8 = [BE32 rom_start][BE32 rom_end]
         저장 위치 = rzip 블록 507 (ROM 0x188328) 압축해제 +0x460
루프     buf = alloc(0x2800) ; load(start, buf, end-start)
         do ProcessGlyph ; ptr += BE32(ptr+4) ; idx++
         while (ptr + 0xF) < (end - start)
```

### ★서술자 end 를 체인 길이에 맞출 것

do-while 이라 마지막 글리프까지 돌려면 여유가 필요하다.

```
glyph94 처리 조건 : (L - size94) + 15 < region_len
그 뒤 종료 조건   : L + 15 >= region_len
=> region_len = L + 15  이면 항상 성립
```

체인이 짧아졌는데 `end` 를 그대로 두면 0 패딩을 글리프로 읽어 `size=0` →
**무한루프 → 부팅 불가**. `build_poc.simulate_boot_loop()` 가 빌드 시점에 막는다.

## 5. 변경 지점 (전부 rzip 블록 3개 + 글리프)

| 대상 | 위치 | 제약 |
|---|---|---|
| 글리프 체인 | ROM `0x40F10` ~ | 영역 `0x42450` 이전, `alloc(0x2800)` 이하 |
| 폰트 서술자 | 블록 507 `+0x460` | — |
| charmap | 블록 507 `+0x2E10` | 95칸, 코드 < 0xA1 |
| 렌더러 | 블록 66 `+0x210`/`+0x21C`/`+0xB2C` | — |
| 대사 | 해당 rzip 블록 | 바이트 길이 **동일** (널 글리프로 패딩) |

★번역 폭 예산은 **메시지 단위**다 — `docs/bubble-width.md`.
말풍선 = `1.15 × (메시지 내 모든 자막의 최대 줄 폭) + 10.35`.
한 자막이라도 미번역으로 남으면 그 영문이 자모 글리프로 측정돼 메시지 전체가 깨진다.

**블록은 줄일 수는 있어도 키울 수 없다.** zopfli 필수 (zlib 은 블록 66 에서
무수정 재압축조차 +1 B).

## 6. 한글 폰트 구성

```
자모 소스   물마루(OFL) Mulmaru.pfp — 조합형 부품 457개
            ⚠️ .pfp 의 data 는 셀 하단 정렬. 위 정렬로 놓으면 종성이 초성 자리에 찍힌다.
셀          12 x 12
슬롯 배분   자모 89 + 문장부호 5(. , ! ? -) + 널 1 = 95
널 글리프   w=1 h=1 xoff=-1 -> advance 0, 완전 투명. 짧은 번역문의 남는 바이트를 채운다.
            (공백으로 채우면 렌더러가 버리지 않아 줄이 넓어진다)
```

### 벌 선택과 배정

- 부품 선택: 픽셀 오차 최소화 탐욕 (`tools/jamo_optimize2.py`) — 89부품
- **배정은 음절 단위로** (`tools/jamo_assign.py`)
  자모를 독립적으로 고르면 납작한 초성이 키 큰 중성과 붙어 깨진다(베).
  조합된 음절 전체의 오차로 고르면 해소된다.
- 현재 품질: 원본 물마루 대비 정확 일치 32.3%, 음절당 평균 픽셀오차 10.48 px (셀 144 px)

### ★통글자 22자 — 커버리지 함정

물마루에는 부품 조합 없이 **직접 그린 통글자**가 22자 있다(`data` 만 있고 `components` 없음):
`래 럐 레 례 뫼 믜 뵈 븨 삐 쏴 쐬 씌 씨 외 의 제 졔 쫘 쬐 쯰 찌 피`.
`build_triples` 가 이들을 조용히 버려 **「의」「래」「씨」 같은 필수 음절이 인코딩 불가**였다.
`build_refs()` 가 통글자의 `data` 를 기준 비트맵으로 넣어 해결 — 부품 선택집합(89칸)은
그대로이므로 **폰트는 바뀌지 않고 배정표만 11,150 → 11,172 로 채워진다.**
